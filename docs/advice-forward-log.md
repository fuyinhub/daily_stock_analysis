# Advice forward log

> Evaluation only. Past performance, including anything this log shows, does not guarantee future results. Nothing here is investment advice, and nothing here places an order or talks to a broker.

`evals/advice_forward_log/` keeps a forward paper log of the advice the system actually published, and scores it later against what prices did next. It calls no LLM and fetches no market data. It does not change any signal, score, threshold or prompt.

## Why it exists

The published `operation_advice` is generated by the LLM. It cannot be regenerated for past dates, so the only honest test is to record each run's advice when it is made and wait. The built-in `BacktestService` does this from `analysis_history`, but a GitHub Actions run starts from an empty `data/stock_analysis.db`, so nothing accumulates there. This log is the durable replacement for that history.

## What is recorded

One JSON line per ticker per analysis record, in one file per run date (`advice-log/YYYY-MM-DD.jsonl`):

| Field | Content |
| --- | --- |
| `run_date`, `logged_at`, `run_id` | When the advice was stored (`analysis_history.created_at`) and which workflow run stored it |
| `ticker`, `universe_id` | Position label in the configured `STOCK_LIST` (`ticker_1`, ...) and a fingerprint of that list |
| `market`, `report_type` | As resolved by the pipeline |
| `advice` | `sentiment_score`, `operation_advice`, `trend_prediction`, `decision_type`, `action`, `action_label`, `confidence_level`, `ideal_buy`, `secondary_buy`, `stop_loss`, `take_profit`, `model_used`, `success`, `report_language` |
| `price_inputs` | `advice_bar_date` (the daily bar the advice refers to, resolved the same way `BacktestService` resolves it), its close, `current_price`, `change_pct`, and the last 30 stored daily bars up to that date (OHLCV) |

Not recorded: stock codes, stock names, and any narrative text (summaries, reasons, news). Records for codes outside `STOCK_LIST` (for example market reviews) are skipped because they have no label.

## How persistence works

The daily workflow (`.github/workflows/00-daily-analysis.yml`) has one extra step after the report push:

1. `run.py export` reads the `analysis_history` and `stock_daily` rows the run just wrote and appends them to day files under `$RUNNER_TEMP/advice-log` (outside `reports/` and `logs/`, so they are not part of the uploaded artifact).
2. `run.py push` appends those rows to the `advice-log/` directory of the private `dsa-reports` repository, using the same `DSA_SYNC_TOKEN` as the report push. It reads the remote file first and only adds rows that are not there yet. Existing rows are never rewritten or removed, and exporting the same record twice adds nothing.

The step is `continue-on-error`: a failure shows as a warning on the run and never fails the analysis. The schedule, the analysis step and the report-push step are unchanged.

## Reading the log after N weeks

- In GitHub: run the **Advice Forward Log Eval** workflow (`workflow_dispatch`). It downloads `advice-log/`, prints the report to the job summary and uploads it as an artifact. The report contains aggregates only.
- Locally, from a clone of the private repository:

```bash
python evals/advice_forward_log/run.py evaluate --log-dir /path/to/dsa-reports/advice-log
python evals/advice_forward_log/run.py evaluate --log-dir /path/to/dsa-reports/advice-log --json-out report.json
```

## Evaluation method

- Entry: the close of `advice_bar_date`. Exit: the close of the 10th following daily bar (`BACKTEST_EVAL_WINDOW_DAYS`). Neutral band 2% (`BACKTEST_NEUTRAL_BAND_PCT`). Same horizon and band as the trend-signal evaluation.
- Forward prices come from the log itself. Every row carries the recent bars of its run, so a row logged 10 or more trading days later holds both the advice-day close and the 10 bars after it. Both prices are taken from that single later snapshot, so they share one price basis. Missed runs are bridged as long as the gap is shorter than the 30-bar window.
- Each row is scored with the existing `BacktestEngine.evaluate_single` (win / loss / neutral, long or cash stance from the advice text).
- Reported per group (all scored rows, stance, `operation_advice`, `decision_type`): sample size, mean, median, share positive, excess over the all-scored mean, and win / loss / neutral counts.
- Benchmark: all scored advice rows, that is the same tickers on the same days regardless of what was advised.
- Advice whose forward window is not in the log yet is counted as pending and never estimated. With fewer than 30 scored rows the report says `INSUFFICIENT DATA`; groups under 30 are flagged individually.
- If the same ticker is analysed more than once for the same daily bar, only the first advice is scored.

## Limitations

- The log starts empty. Nothing can be scored until 10 trading days after the first logged run, and a meaningful sample needs many weeks of daily runs. A few dozen overlapping rows from one month are not evidence of anything.
- Consecutive daily windows overlap, so rows are not independent; no significance test is reported.
- The watchlist is user-chosen and small. Results describe these tickers in this period only.
- Labels are positions in `STOCK_LIST`. Editing or reordering the list changes `universe_id` and starts new series; advice from the last 10 trading days before the change stays pending forever. The price series in the log could be matched to public data, so the labels are a courtesy, not strong anonymisation. The log is written only to the private repository.
- Prices are whatever the data source returned at run time. If a later snapshot shows the advice-day close on a different basis (split, dividend adjustment, or a run before the close), the return still uses the later snapshot consistently, but that row's stop-loss and take-profit levels are not applied.
- Close-to-close returns, no costs, no slippage, no trading halts.
- A run that fails before storing its analysis, or a failed push, leaves no row for that day.
